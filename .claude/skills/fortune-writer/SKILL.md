# fortune-writer

fortune-commit은 매일 커밋해야 열리는 포춘쿠키 위젯이다. 운세는 쿠키를 연 사람이 받는 작은 보상이라서, 피식 웃고 기분 좋게 하루를 시작하게 만드는 것이 목적이다. 문구 수백 개를 여러 번에 나눠 쓰게 되므로, 언제 써도 같은 톤과 품질이 나오도록 이 규칙을 따른다.

## 문구 규칙

**형식**
- 한국어는 `오늘 ~할 거예요`처럼 **오늘 일어날 일을 점치는** 문장으로 쓴다. 뒤에 "진짜로요.", "좋은 쪽으로요." 같은 짧은 한마디를 붙이면 더 웃기다.
- 자연스러운 존댓말(~거예요, ~예요). "~할 것입니다", "~하리라" 같은 딱딱한 말투는 쓰지 않는다.
- 영어는 같은 뜻의 자연스러운 영어로 쓴다. 직역보다 영어 개발자가 읽고 웃을 표현이 낫다. (`Today, ...` / `... will ...`)
- **ko와 en은 같은 번호끼리 같은 뜻이다.** 위젯이 같은 번호를 골라 언어만 바꾸기 때문이다. 한쪽을 고치면 다른 쪽도 고친다.
- 위젯 쪽지에서 **3줄을 넘지 않는다.** (아래 검사 스크립트로 확인)

**톤**
- 개발자라면 아는 상황으로 웃긴다: PR, 머지 충돌, CI, 세미콜론, 고무 오리, Stack Overflow, `git stash`, 캐시, 정규식, 회의, 레거시, 배포 금요일.
- 사주·오행·귀인 같은 운세 말투를 개발 상황에 섞으면 이 서비스다운 문구가 된다. (예: "금(金)의 기운이 들어와서 저장소에 별이 쏟아질 거예요.")
- 쿠키는 **커밋한 사람**이 연다. "오늘은 쉬어도 돼요"처럼 커밋과 어긋나는 말은 쓰지 않는다.
- 피할 것: 특정 회사·사람·언어 비하, 외모·건강·돈 이야기, 정치, 성적인 농담, 지나치게 어려운 내부 농담.

## 등급별 문구 (v3.1부터)

등급은 아이디 + 날짜 해시로 먼저 정해지고, 그 등급의 문구 풀에서 하나가 나온다. 그래서 문구가 등급과 맞아야 한다.

| 등급 | 키 | 문구 느낌 | 예 |
|---|---|---|---|
| 전설 ✨ | `legend` | 말도 안 되게 좋은 일, 과장된 축복 | "오늘 올린 코드가 리뷰어 전원에게 LGTM을 받고 전설로 남을 거예요." |
| 대길 | `daegil` | 아주 좋은 일 | "오늘 올린 PR이 커피가 식기 전에 승인될 거예요." |
| 길 | `gil` | 좋은 일 | 지금 `src/fortunes.js` 문구들이 대부분 여기 |
| 중길 | `junggil` | 소소하게 좋은 일 | "오늘은 빌드가 평소보다 10초 빨리 끝날 거예요." |
| 소길 | `sogil` | 작지만 다행인 일, 살짝 웃픈 일 | "버그를 만나지만, 재현이 쉬울 거예요." |
| 흉 | `hyung` | 나쁜 일 + **위로나 반전** (커밋하면 액땜) | "머지 충돌이 찾아올 거예요. 하지만 오늘 커밋했으니 액땜은 끝났어요." |

흉도 사용자를 기분 나쁘게 하면 안 된다. 나쁜 일은 가볍고 개발자다운 것(충돌, 빨간 CI, 오타)으로 하고, 뒤에 커밋한 것을 칭찬하거나 반전을 둔다.

## 특별 운세 (v3.1부터)

그날에만 나오는 문구다. 키는 `season.spring`, `weekday.mon`, `day.halloween`처럼 쓴다.
- 계절(봄·여름·가을·겨울), 요일(월요일·금요일)
- 기념일: 설날, 추석, 만우절, 프로그래머의 날(9월 13일), 할로윈, 크리스마스, 12월 31일
- 그날이라는 걸 바로 알 수 있게 쓴다. ("금요일 배포는 오늘만큼은 무사할 거예요.")

실제 파일 구조는 v3.1 구현에서 정해진 것을 먼저 확인하고 따른다. (`src/fortunes.js` 맨 위 주석과 `tests/pick.test.js`)

## 작업 순서

1. **지금 문구 확인**: 늘리거나 고칠 파일을 읽고, 이미 있는 소재를 파악한다. 같은 농담을 또 쓰지 않기 위해서다.
2. **초안 쓰기**: 초안을 JSON 파일로 scratchpad에 저장한다. 모양은 `{ "daegil": { "ko": [...], "en": [...] }, ... }` 또는 `{ "ko": [...], "en": [...] }`.
   한 번에 많이 써야 하면 소재를 먼저 나눈다(코드 리뷰, 배포, 디버깅, 협업, 공부, 도구…). 그래야 비슷한 문구가 몰리지 않는다.
3. **검사하기**: 저장소 맨 위 폴더에서 실행한다.
   ```
   node .claude/skills/fortune-writer/scripts/check-fortunes.mjs <초안.json>
   ```
   ko/en 개수, 3줄 넘김, 지금 문구·초안끼리 겹치거나 80% 넘게 비슷한 것, 운세 표현(~거예요) 빠짐을 잡는다. 걸린 문구는 고쳐서 다시 돌린다.
4. **검수받기**: 문구는 2sseul이 직접 검수한다. (PRD 원칙: AI 초안 → 2sseul 검수) 아래처럼 표로 보여준다. 많으면 등급이나 소재별로 나눠 보여준다.

   | # | 등급 | 한국어 | English |
   |---|---|---|---|
   | 1 | 대길 | 오늘 올린 PR이 커피가 식기 전에 승인될 거예요. | Your PR will be approved before your coffee gets cold. |

   "고칠 번호와 이유를 알려 주세요. 괜찮으면 반영할게요."라고 묻고, 승인 전에는 `src/`에 넣지 않는다.
5. **반영하기**: 승인된 문구를 파일에 넣고 `npm test`로 확인한다. 그리고 `todo-log` 스킬로 체크와 기록을 남긴다. 검수에서 바뀐 것(뺀 문구, 고친 이유)은 `[수정]`으로 기록하면 README의 변경 내역 재료가 된다.
